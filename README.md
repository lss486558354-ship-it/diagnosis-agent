# 设备故障诊断 Agent

> 把工业设备的整套技术文档变成**可检索、可溯源**的知识库，再通过 MCP 暴露给
> AI Agent 直接调用。每条结果都带出处路径 —— 而不是丢给你一段看起来相关的
> 文字让你自己判断。
>
> 从关键词 → 到可溯源 → 到**会说「我不知道」** → 到**能被证伪**。

**当前状态**：语料 / 检索 / MCP 服务 / 故障案例库 / 评估层 均已完成 ✅ · LangGraph 诊断编排 未开始

---

## 这个项目解决什么问题

我做过两套工业设备的控制系统，每套都写了几十万字的技术文档。但真实场景是这样的：

```
现场设备停了 → 翻开 200KB 的文档 → Ctrl+F 搜"丝杆" → 翻到 37 处提及
             → 逐个看，判断哪一处讲的是"卡住"而不是"参数设置"
             → 20 分钟后找到答案
```

**文档写得很全，但排查故障时还是靠人肉翻。** 这是这个项目要解决的事。

难点不在于「把文档塞给大模型」，而在于三件具体的事：

1. **符号型术语检索不准**。用户搜 `0x30`，如果索引里只剩 `0` 和 `x30` 两个碎片，检索必然失败。
2. **检索结果不可信**。给一段文字而不给页码，用户没法判断该不该信——这在故障排查场景是致命的。
3. **不肯说「不知道」**。库里没有的东西，向量检索照样返回最近邻，还带着看起来完全站得住脚的引用。

第 3 条是做的过程中才意识到比前两条更危险的，见下面「四、门控」。

## 快速开始

```bash
# 依赖：jieba + numpy（MCP SDK 与 Ollama 若已装则无需重复）
pip install jieba numpy

# 拉取中文 embedding 模型（约 1.2GB，一次性）
ollama pull bge-m3

# 建索引（实测 12 秒 / 288 块）
python build_index.py

# 查询
python demo_search.py "启动工艺的命令是什么"
python demo_search.py "丝杆限位开关失效导致流程卡住" -k 3
python demo_search.py --compare "限位开关失效"     # 三路对比
python demo_search.py                              # 交互模式

# 跑评估（重建索引或改检索逻辑后重跑，数字可横向比较）
python eval/run_eval.py        # → eval/report.md + eval/results.json

# 并发回归测试（真实库不受影响，用临时库）
python smoke_test.py
```

**接进 Claude Code**：

```bash
claude mcp add -s user equipment-diagnosis -- python /绝对路径/mcp_server.py
claude mcp list        # 应显示 ✔ Connected
```

> ⚠️ 用 **user scope**，不要把 `.mcp.json` 放在子目录里 —— 实测 Claude Code
> 对子目录下的 `.mcp.json` **不读、不报错、不提示**，只会表现为「重启没反应」。

## 五个关键设计决策

### 一、分块：按标题切，表格绝不拆

常见的 512 字定长切分在这个语料上会毁掉两类知识：

```
❌ 定长切分的后果
  块 1 结尾：| `CMD_PROCESS_START` (0x30) | `AA 30 00
  块 2 开头：CS` | 开始工艺流程 |
  → 任何一块单独看都答不出"启动命令是什么"
```

本语料有 **991 行表格、541 个标题**——正是知识密度最高的部分。所以：

| 规则 | 原因 |
|------|------|
| 按 h1/h2/h3 标题切 | 标题已给出天然语义边界 |
| 表格整体保留（超长也不拆） | 切开的命令表等于作废 |
| 代码块与所属段落绑定 | 孤立的 `AA 30 00 9A` 零信息量 |
| 超长块按 **Block 分组**切 | 边界只落在表格*之间*，不落在表格内部 |
| 碎块向上归并到共同父级 | 本语料大量叶子小节只有一两句话 |

**实测**：288 块，中位块长 **434 字符**，短于 180 字符的仅 14 块（4.9%）。

### 二、分词：位置映射法，不做占位符替换

`CMD_PROCESS_START`、`0x30`、`PA9`、`115200`、`6s` 这类符号 token 一旦被切碎就永久丢失。

**走过的弯路**：最初把术语替换成占位符再还原，失败了——占位符在跨工具传递时容易被剥掉，还原必然失效，9 项术语检查全部 FAIL。

**最终方案**是位置映射：先扫描出术语的字符区间，再让 jieba 返回每个词的 `(start, end)`，落在术语区间内的碎片直接丢弃，术语本身按位置插回。

```
输入: 启动工艺的命令 CMD_PROCESS_START 是 0x30
输出: ['启动', '工艺', '命令', 'cmd_process_start', '0x30']
      └──── jieba 通道 ────┘  └── 术语通道 ──┘
```

术语完整性检查 **9/9 通过**。

另有一次修正是补回被停用词表丢掉的**否定词**：`不`、`无` 被当停用词删掉后，
「不响应」退化成「响应」，语义直接反转 —— 在故障排查场景里这是会误导维修动作的错。

### 三、检索：混合 + RRF —— 以及一次被自己数据推翻的假设

**设计意图**：两路的短板正好互补。

| | 擅长 | 短板 |
|---|---|---|
| BM25 | `0x30`、`PA9` 这类精确字面 | 「丝杆不动」匹配不上「丝杆堵转」 |
| 向量 | 「丝杆不动」≈「丝杆堵转」 | 对专有名词和精确字面不敏感 |

**为什么用 RRF 而不是加权求和分数**：BM25 分数无界（本语料实测到 **17.56**），余弦相似度固定在 [-1,1]。归一化后加权求和看似合理，实则脆弱——归一化依赖当次查询的结果分布，同一文档在不同查询下权重会漂移。

RRF 只用**排名**，排名是跨检索器可比的：

```
score(d) = Σ  weight_r / (k + rank_r(d))        k = 60
```

**设计意图是**：RRF 奖励**共识** —— 两路都认可的结果，比只有一路力挺的更可靠。

**但实测否定了它。** 30 题四配置跑下来：

| 配置 | Recall@5 | MRR@5 | 平均耗时 |
|---|---|---|---|
| 纯关键词 (BM25) | **80.0%** | **0.583** | 15 ms |
| 纯向量 (语义) | 70.0% | 0.452 | 45 ms |
| 混合 (RRF) | **80.0%** | 0.543 | 41 ms |
| 混合 + 门控 | **80.0%** | 0.543 | 44 ms |

Recall 打平，**MRR 反而更低**。不是"没测出来"，是测出来确实没赢。

机制能算到具体块，不是推测。最典型的一道是「0xAA 帧的校验怎么算」：

| 融合名次 | BM25 排名 | 向量排名 | RRF 分 | |
|---|---|---|---|---|
| 1 | #6 | #1 | 0.03154 | |
| 2 | #1 | #9 | 0.03089 | |
| 3 | #3 | #7 | 0.03080 | |
| 4 | #8 | #3 | 0.03058 | |
| 5 | #10 | #4 | 0.02991 | |
| 6 | #4 | #11 | 0.02971 | ← **正确答案** |

正确答案一路 BM25 #2、一路向量 #11，单看哪一路都觉得稳进前五，
**却被 5 个「两路都排在前 10」的块挤到第 6。**

规律很清楚：**RRF 是排名求和，两路均衡的块必然胜过「一路好一路差」的块。**
这是它的设计意图，不是 bug。只是在这个语料上意图落了空 ——
BM25 的第一名本来就很准（top-1 命中 43.3%），融合反而把这个优势摊平了。

**我没有因此改默认权重。** 扫描显示 1.5~5.0 都能到 83.3%，但那是
**在同一套 30 题上选的** —— 改了就成了对这套题的拟合，不是改进。
要支撑改默认值，需要一套不参与调参的验证集。那是下一步的事。

### 四、门控：让系统会说「我不知道」

RAG 最危险的失败不是"答不上来"，是**拿一堆看似相关的东西硬答**。

测试时问「冰箱不制冷怎么修」——知识库里没有任何冰箱文档，但向量路照样返回了
3 条最近邻，每条都带来源路径。**带引用的幻觉比没有引用更危险，因为引用本身就是可信度信号。**

门控的判据：把查询分词，**多字词在全库零命中**时直接判空，不给结果。

实测（`eval/report.md` 第七节）：

- 10 条零词汇重叠的库外问题（冰箱、洗衣机、电梯、路由器…）：**10/10 拦下**
- 30 道正样本：**误杀 0** —— 门控没有为了拦负样本牺牲任何一道真题

**已知边界**：判据是「零命中」，所以只要查询里的词碰巧在语料里出现过，门控
**按设计就不拦**。「打印机卡纸」就是例子 —— 语料里真有一个 3D 打印机项目，
「打印机」三个字命中，门控放行。**这类问题拦不住，而且恰恰最危险**，
因为返回的无关内容带着看起来完全站得住脚的引用。

我没有去调这个判据的阈值。分数区间实测是重叠的，而且「用词不同」与
「库里确实没有」在零命中判据下**本来就不可区分** —— 那是判据的结构性边界，
拧参数治不了。真要治它得**加一层**（向量相似度兜底），而不是继续拧现有参数。

### 五、案例库：经验优先于文档

文档写的是「应该怎么接」，案例记的是「实际踩过什么坑」。两者不能互相替代。

`case_store.py` + **28 条种子案例**（14 条有确定根因 / 14 条排查清单），
从 6 份文档的故障章节里提取，症状字段加权 ×2。

**为什么要有 `kind` 字段**：清单类案例（如「异响排查清单」）没有唯一答案，
把它算进 Top-3 命中率会人为压低分数。分开统计，命中率才是可信的。

实测（**换词**查询，不直接用症状原文 —— 用原文等于把答案抄进题目）：

- Top-1 命中 **12/14**
- Top-3 命中 **14/14**

## 评估：把「看起来」换成「测出来」

手挑的查询永远看起来还行。这个项目里所有关于检索效果的断言，都来自
`eval/` 下一套**可重跑**的评估，而不是"我试了几个查询感觉不错"。

**评估集**：30 道检索题（命令码 8 / 接线 6 / 故障 6 / 参数 5 / 综合 5）
+ 14 条案例换词查询 + 14 条门控负样本（分两组）。

每题带一组**唯一性高的标识符**作为答案特征串 —— 用 `CMD_PROCESS_START`
而不是 `0x30`（后者在命令表里到处都是，命中了也说明不了任何事）。
这样"对不对"不依赖主观判断：你搜一下那个串在不在语料里，
就能验证 ground truth 本身有没有写错。

脚本启动时**自检**：任何特征串在整个语料里搜不到，直接报错退出。
防止把答案写成语料里根本不存在的东西 —— 那就成了"所有方案都答不对"的假失败。

### 两路的失败模式确实互补

| top-k | 纯 BM25 | 纯向量 |
|---|---|---|
| 1 | 43.3% | 33.3% |
| 3 | 80.0% | 50.0% |
| 5 | 80.0% | 70.0% |
| 50 | 93.3% | **100.0%** |

BM25 命中就排得很前，但有一部分答案它**到 k=50 仍召不回**（6.7%）；
向量几乎什么都召得回，但 top-3 只有 50% —— 那是排序问题。

**两路的短板是真互补的，融合的思路站得住。方法对，默认参数没调。**

### 这份报告不能说明什么

写在最显眼的地方，因为它比结论重要：

1. **题目是我看着语料出的**，写题时会不自觉地避开已知的弱点 —— 存在选择性偏差。
2. **30 题覆盖 288 块，抽样率约 10%**，不能外推成整体准确率。
3. 判定是**宽松**的：块里出现标识符即算命中，不等于模型能从中读出正确答案。
   上游检索对了、下游模型答错，是这份报告**测不到**的失效模式 ——
   那一层另有人工抽验协议，见 `eval/模型层抽验清单.md`。

所以这些数字的正确读法是「**下限参考**」：真实使用只会更差，不会更好。

### 一处主动交代的口径修正

判定条件在开发过程中改过一次。早期版本只在块的**正文**里找标识符，于是
「上位机通信协议 > 4.1 直流电机启动 — CMD_DCM_START」这种**标识符只出现在标题里**
的块被判成未命中 —— 可 `mcp_server.py:138` 把结果渲染成 `### [{i}] {title_str}`，
标题本来就是呈现内容的一部分。

那是**我评估口径的错，不是检索的错**。改为一并匹配标题后：纯 BM25 从 76.7%
升到 80.0%，混合从 76.7% 升到 80.0%。

**分数是往上走的，所以专门写在这里。** 可以佐证的是：核心结论
（混合在默认权重下没有跑赢纯 BM25）在**两种口径下都成立** ——
只有在一个口径下才成立的结论，才有理由怀疑它来自测量误差。

## 已知限制

如实记录，避免误导：

- **语料仅约 178K 字符**，覆盖范围有限。文档里没写的，这套系统答不出来 ——
  检索不是生成，它不会编，但也补不了空白。
- **18 个块超过 1400 字符**（最大 6906，是 ASCII 工艺流程图）。这是**有意的取舍**：
  按行切 ASCII 图会把它变成语义残片，不如整体保留。代价是这些块的向量语义会被
  稀释 —— 这个影响**至今未量化**，原计划在评估阶段做，实际没做。
- **RRF 的 k=60 未针对本语料调优**。这个值来自文献惯例。权重扫描做的是
  `weight` 而不是 `k`，所以「不同 k 值的影响」这一项**也未做**。
- **同义词表是手工维护的 16 条**，覆盖面有限，且是拍脑袋列的——它解决的是
  我遇到过的具体换词问题，不是完整方案。
- **未做重排序（rerank）**。两路召回后直接融合，没有跨编码器精排。
  这是下一步，但要先评估它是否值得那个延迟。
- **`search_command` / `get_wiring` 拆成独立工具是否有用，未验证**。
  技术上它们就是 `search_doc` + 预设表格过滤，拆开的理由是"MCP 的工具描述
  本身就是给模型的提示"。这个假设**没有实测过** —— 如果 6 工具与单工具的
  选对率没差别，就该合并。
- **并发测试只覆盖「6 线程 × 一轮调用」**。6 这个数字是手工指定的，不是
  MCP SDK 真实线程池的规模。未覆盖长时间运行后的连接状态、高频反复调用、
  写入事务中途失败后的回滚。

## 这个项目里我踩过并且记录下来的坑

放在最后，因为它是这个项目**方法上**最想传达的东西：

| 坑 | 怎么发现的 |
|---|---|
| 判定口径漏了标题 —— 正确答案被判成失败 | 看 top-2 结果的标题里**就写着答案** |
| `_ranks_for_item` 取了「下标最小」而非「排名最好」的块 —— 诊断被引向错误方向 | 命令表在三份文档里各有一份，按下标取等于随机 |
| 语料一行 `0x0466 (dec=1150 = 1024+126)` 三个数互相对不上 | 核验模型输出时撞上，回溯原始 CSV 查到真值 `0x0486` |
| **差点冤枉模型编造** —— 判「编造」前 grep 提前收工 | 复查时发现答案在同一份文档往下 6 行 |
| 3 个工具因 SQLite 跨线程崩溃 | 真实会话中暴露，前两层测试**一个都没测出来** |

最后一条尤其值得记：**并发这一类缺陷，在单元测试和协议测试这两层是结构性不可见的。**
它们只在真实会话里现形。
