## 九、结论与局限

**实测结论（含一条与预期相反的）：**

1. ⚠️ **混合在默认权重下没有跑赢纯 BM25** —— Recall 打平（80.0%），MRR 反而更低（0.583 → 0.543）。不是「没测出来」，是测出来确实没赢。
   机制可以直接算出来，不是推测。最典型的一道是「0xAA 帧的校验怎么算」：正确答案一路 BM25 #2、一路向量 #11，单看哪一路都觉得稳进前五，实际却被融合挤了出去。逐块摊开：

   | 融合名次 | BM25 排名 | 向量排名 | RRF 分 | |
   |---|---|---|---|---|
   | 1 | #6 | #1 | 0.03154 |  |
   | 2 | #1 | #9 | 0.03089 |  |
   | 3 | #3 | #7 | 0.03080 |  |
   | 4 | #8 | #3 | 0.03058 |  |
   | 5 | #10 | #4 | 0.02991 |  |
   | 6 | #4 | #11 | 0.02971 | ← **正确答案** |

   规律很清楚：**挤掉它的块，两路都排在前面；而正确答案一路高一路低，哪一路都不够突出。** RRF 是排名求和，两路均衡的块必然胜过「一路好一路差」的块 —— 这是 RRF 的设计意图，不是 bug。只是在这个语料上意图落了空：BM25 的第一名本来很准（top-1 命中 43.3%），融合反而把这个优势摊平了。


2. **但两路的失败模式确实互补**，融合的思路本身站得住：BM25 即使把 k 拉到 50，仍有 6.7% 的题**根本没有召回**；向量 top-50 能到 100.0%，但 top-3 只有 70.0%（排序问题）。换句话说：**方法对，默认参数没调。**
3. 权重扫描印证了上一条：1.0/1.0 处于最差一档，多个更偏 BM25 的取值都能到 83.3%。但该结果来自评估集自身，**不作为改默认值的依据**。
4. 门控零误杀：10/10 条零词汇重叠的库外查询被拦下，30 道正样本一道没伤。有词汇重叠的 4 条全部放过 —— 这是零命中判据的固有边界，已在第七节标明。

**这份报告不能说明什么：**

1. **题目是我看着语料出的**，写题时会不自觉地避开已知的弱点，存在选择性偏差。
2. **30 题覆盖 288 块，抽样率约 10%**，不能外推成整体准确率。
3. 判定是**宽松**的：块里出现标识符即算命中，不等于模型能从中读出正确答案。
   上游检索对了、下游模型答错，是这份报告**测不到**的失效模式 ——
   那一层需要人工抽验，见 `eval/模型层抽验清单.md`。

**一处必须主动交代的口径修正：**

判定条件在开发过程中改过一次。早期版本只在块的**正文**里找标识符，于是「上位机通信协议 > 4.1 直流电机启动 — CMD_DCM_START」这种**标识符只出现在标题里**的块被判成未命中 —— 可 `mcp_server.py:138` 把结果渲染成 `### [{i}] {title_str}`，标题本来就是呈现内容的一部分。那是我评估口径的错，不是检索的错。

改为一并匹配标题后：纯 BM25 从 76.7% 升到 80.0%，纯向量维持 70.0%，混合从 76.7% 升到 80.0%，门控误杀维持 0。

**分数是往上走的，所以专门写在这里。** 可以佐证的是：核心结论（混合在默认权重下没有跑赢纯 BM25、MRR 反而更低）在**两种口径下都成立** —— 只有在一个口径下才成立的结论，才有理由怀疑它来自测量误差。

所以以上数字的正确读法是「**下限参考**」：真实使用只会更差，不会更好。
